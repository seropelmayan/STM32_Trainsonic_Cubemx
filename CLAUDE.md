# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

`Trainsonic` is STM32 firmware for sensored **Field-Oriented Control (FOC)** of a single PMSM,
originally generated by **ST Motor Control Workbench (X-CUBE-MCSDK v6.4.2)** on STM32CubeMX.
Target MCU: **STM32G431CBTx** (Cortex-M4F, hard-float `fpv4-sp-d16`, 128 KB flash / 32 KB RAM).

**The machine is a smart cable strength trainer** — a 20-pole-pair, ~700 rpm direct-drive
surface-PM motor on a 15S pack driving a cable drum. The user pulls a handle against a
programmable resistance ("weight"), and the drum retracts the cable between reps. The ESP32
side lives in a separate repo (`smart trainer/.../trainsonic-firmware`) and owns the weight
setting and UI; this firmware is the motor drive.

Two consequences of that product shape explain almost all the unusual code here:

- **Force is felt by a human hand**, so cogging and torque ripple are product defects, not
  academic ones. Hence anti-cogging feed-forward, encoder-latency compensation, and a long
  documented history of bench A/Bs on "feel".
- **A pull REGENERATES.** The user does work on the motor, so power flows *into* the pack on
  every rep; the drum only draws power when retracting or holding. Get this backwards and you
  will "fix" the energy-management code in exactly the wrong direction.

(Historical note: the project was once named `Ropetow`, most hand-written functions are still
`Ropetow_*`, and older comments/docs describe it as a "rope-tow / winch drive". That framing was
inferred from the motor profile and is **wrong** — it inverts the power flow above.)

**The generated MCSDK core is a minority of the interesting code.** Most of what you will be
asked to change lives in hand-written blocks inside (and, importantly, *outside*) the generated
files. Read "Regeneration" below before touching anything.

## Branches

- `mcsdk-ff-fw` — **the live branch.** All flux-weakening/governor work, the raised 29 A current
  limit, and the audit docs are here.
- `main` — 20 commits behind, ends at the ESP-link commit. Do not develop against it.

## Build / flash / debug

- **No command-line build exists in this tree** (no Makefile). Building is **STM32CubeIDE** only;
  `STM32CubeIDE/` is the Eclipse project. A headless build is possible via
  `stm32cubeidec --launcher.suppressErrors -nosplash -application org.eclipse.cdt.managedbuilder.core.headlessbuild -build Trainsonic/Debug`
  but the GUI is the normal path.
- **`STM32CubeIDE/.project` links every source file individually** (88 `<link>` entries). A new
  `.c` file in `Src/` is **not** compiled until you add a link entry:
  ```xml
  <link><name>Application/User/foo.c</name><type>1</type>
  <locationURI>PARENT-1-PROJECT_LOC/Src/foo.c</locationURI></link>
  ```
  Headers in `Inc/` need nothing (include path). A regen has silently dropped links before —
  commit `adfce43` was a repair of exactly this.
- **There are no unit tests, no linters, and no package scripts.** "Testing" in this project means
  flashing the board and reading the USB-CDC console — the tuning rigs below are the test harness.
- Compile defines: `ARM_MATH_CM4`, `USE_HAL_DRIVER`, `STM32G431xx`.

## Regeneration: the single most dangerous operation in this repo

The `.ioc` / `.ioc.wb` / `.wbdef` still drive code generation, but **this tree can no longer be
regenerated safely without a manual merge**. Two reasons:

1. Normal MCSDK rules apply — hand code must sit between `/* USER CODE BEGIN x */` … `END x` or
   `USER SECTION BEGIN/END`.
2. **Critical hand-written code lives OUTSIDE those guards**, inside the generated body of
   `FOC_CurrControllerM1()` in `Src/mc_tasks_foc.c`: the SPI-encoder commutation extrapolation
   (without it commutation breaks), the Iq/Id low-pass, dead-time compensation, the step-capture
   rig, and the `FW_DataProcess()` call that the flux-weakening loop depends on. Regeneration
   overwrites all of it.

**Before regenerating, read [REGEN_CHECKLIST.md](REGEN_CHECKLIST.md) and
[REGEN_INTEGRATION.md](REGEN_INTEGRATION.md) top to bottom.** They encode hard-won bench history:
which blocks to re-merge, which hand-edits to generated headers to re-apply (PID gains,
`hMaxReliableMecSpeedUnit` in `mc_config_common.c`, the 29 A `NOMINAL_CURRENT_A`), and known
regressions a regen re-introduces. Commit first — the procedure is "diff the regenerated files
against the previous commit and merge back".

Note: `REGEN_INTEGRATION.md` predates the current hardware and still states `AMPLIFICATION_GAIN`
must be 20 / ±16.5 A. That is stale — see the invariants table below.

## Hardware ground truth

These are bench-verified. Do **not** "correct" them toward datasheet or placeholder values.

| Quantity | Value | Notes |
|---|---|---|
| Current sensing | **Three-shunt**, low-side | Not ICS. `RSHUNT = 0.005 Ω` |
| CSA gain | **10 V/V** | `AMPLIFICATION_GAIN` (power_stage_parameters.h) **must equal** `DRV8353_CSA_GAIN_CODE` (drv8353.h, `0x1` = 10 V/V). Change both together — a mismatch silently mis-scales every current in the system |
| Pole pairs | **20** | electrical angle = mechanical × 20 |
| Encoder | **AS5047P** 14-bit SPI (16384 cnt/rev), + 1024-PPR ABI into TIM3, + index on PB3 | FOC commutates on the **SPI angle**, not TIM3 |
| Measured motor params | **L = 1.10 mH, λ = 0.0178 Wb, Ich ≈ 16 A** | headers still carry the profiler's `LS = 0.0014`; the measured values are the durable result of the FF trials |
| Rates | 25 kHz PWM / current loop · 1 kHz medium-frequency (speed) task | `PWM_FREQUENCY`, `SPEED_LOOP_FREQUENCY_HZ` |
| Bus | 13S, `NOMINAL_BUS_VOLTAGE_V 60` | audit computes a ~75 V uncontrolled-rectification ceiling at max pull speed |

Known open hardware issue: the encoder magnet is mounted on a **ferromagnetic (hardened steel)
shaft**, which AMS explicitly says to avoid. This is the root of the weak AGC (~216–246),
`enc=BAD` flapping, and much of the residual roughness. See
[MAGNET_MOUNT_REPORT.md](MAGNET_MOUNT_REPORT.md). Don't chase encoder noise in software without
knowing this.

## Architecture

### Layers (outer → inner)
1. **`Src/main.c`** — CubeMX init (170 MHz from 24 MHz HSE), then FreeRTOS. The `while(1)` is
   empty; everything runs in tasks and ISRs.
2. **`Src/mc_api.c` / `Inc/mc_api.h`** — the MCSDK public motor API (`MC_StartMotor1()`,
   `MC_ProgramSpeedRampMotor1[_F]()`, `MC_SetCurrentReferenceMotor1()`, …). One motor, "M1".
3. **`Src/mc_tasks.c` + `Src/mc_tasks_foc.c`** — scheduler + state machine. **`mc_tasks_foc.c` is
   the heart of this project** (~94 KB): the stock MF task and current controller, plus nearly all
   the custom control work.
4. **`MCSDK_v6.4.2-Full/…/MCLib`** and **`Drivers/`** — vendor code, unmodified. Don't edit.

### Threads and ISRs — the context map that matters
Getting this wrong is the classic bug here (e.g. HAL SPI reads hang in the priority-0 FOC ISR).

| Context | Rate | What runs there |
|---|---|---|
| `TIM1_UP_TIM16_IRQn`, prio **0** | 25 kHz | `FOC_CurrControllerM1` — current loop, commutation angle extrapolation, **anti-cogging FF lookup (interpolated, since 2026-09-08)**, dead-time comp, `FW_DataProcess`, step capture. **Never block this.** |
| `ADC1_2_IRQn`, prio 2 | 25 kHz | current-reading completion feeding FOC |
| `TIM3_IRQn`, prio 3 | — | encoder ABI |
| `TIM1_BRK_TIM15_IRQn`, prio 4 | — | PWM break / overcurrent |
| `USART2_IRQn`, prio 6 | — | ESP32 link RX bytes (deliberately below all control ISRs) |
| `mediumFrequency` task | 1 kHz | MCSDK MF task (state machine, **speed PI = the torque-limited governor**) → `FOC_CalcCurrRef` (speed-source override, FW, legacy governor when `#`) → then `MC_APP_PostMediumFrequencyHook_M1` (encoder → position servo → ESP link: heartbeat → `Ropetow_SpeedWindowApply`) |
| `appTask` (`StartAppTask`, prio Low) | 50 ms | USB CDC bring-up, DRV8353 + AS5047 init, auto-start, status logging, and executing CDC command requests |

ISR bodies: `Src/stm32g4xx_mc_it.c`, `Src/stm32_mc_common_it.c`.

`Src/mc_app_hooks.c` is the sanctioned extension point and is where the custom subsystems are
attached: `MC_APP_BootHook()` → `Ropetow_CoggInit()` + `Ropetow_McFwInit()`;
`MC_APP_PostMediumFrequencyHook_M1()` → `Ropetow_EncoderUpdate()` → `Ropetow_PositionControl()`
→ `Ropetow_EspLinkService()`, **in that order** (the servo must see the freshly published angle).

Ordering caveat, already diagnosed in [SMOKING_GUN_findings.md](SMOKING_GUN_findings.md): the
encoder hook runs *after* the MF task, so `FOC_CalcCurrRef` reads the **previous** cycle's
`g_enc_mech14` — the anti-cogging lookup is ≥1 ms stale and, unlike commutation, is not
velocity-extrapolated. That is why the map cancels at calibration speed (~9 rpm) but not at pull
speed.

### The custom subsystems (all hand-written, all in `mc_tasks_foc.c` unless noted)
- **Encoder path** — `Ropetow_EncoderUpdate()` reads the AS5047 over SPI in *thread* context, then
  the 25 kHz ISR extrapolates that angle forward (`g_enc_theta0 + g_enc_omega_tick·(dt + g_enc_ff_ticks)`)
  to compensate commutation latency. Optional PLL velocity observer and a fitted 2-harmonic INL
  (eccentricity) correction, both off by default. `Src/as5047.c`.
- **Anti-cogging** — 512-bin position-indexed Iq feed-forward (`Inc/cogg_table.h`), self-calibrating
  via a servo sweep with ILC refine passes and optional harmonic denoise. Persisted to **flash page
  63 (`0x0801F800`, magic "CG21")** and reloaded at boot. Host-side analysis in `cogging.py`.
- **Flux weakening** — two implementations coexist: ST's native voltage-feedback FW (hand-instantiated
  by `Ropetow_McFwInit()`, **on at boot**) and a legacy constant-Id block (`g_fw_*`, off at boot).
  FW is a transient handler for max-effort pulls, not part of the normal envelope.
- **Speed-window control** (2026-09-08, `Ropetow_SpeedWindowApply`) — the drive runs in MCSDK
  **speed mode** with the speed PI's output limits set from every heartbeat: reference =
  `min(heartbeat speed_rpm, g_spdcap_hard_rpm 550)` signed by the drive direction, `lo`/`hi` =
  drive-side / brake-side torque limits. Below the cap the PI is saturated on the drive limit,
  so pull, hold and a hand-controlled eccentric feel exactly the commanded weight (pure torque
  mode); only a released drum running faster than the reference eases off and, if allowed,
  brakes. Kp is recomputed per heartbeat so the full-drive-to-full-brake fade spans
  `g_spd_band_rpm` (120) at any weight. This is ST's prescribed "speed control with torque
  limit" (`PID_Set{Lower,Upper}OutputLimit` on `PIDSpeedHandle_M1`). Wire contract:
  [SPEED_WINDOW_ESP_PATCH.md](SPEED_WINDOW_ESP_PATCH.md). Flux weakening is bound to a shadow
  PID so it cannot overwrite the speed PI limits.
  **The board boots into the legacy scheme and the ESP selects this one per heartbeat**: a
  v4 frame (10 B, carries `brake_mA`) runs the speed window, a v3 frame (8 B) or a
  `TSL_MSG_SETPOINT` runs the legacy governor, so this image in front of an unmodified ESP
  behaves exactly like the old one. CDC `#` toggles *and pins* the scheme for bench A/B
  (`g_ctrl_scheme_lock`; `[m]` then shows `sch=S*`). Reset clears the pin.
- **Legacy overspeed governor** — `g_spdcap_*` hand-written roll-off + P/I brake inside torque
  mode, `g_ctrl_scheme = 0`: the **boot default**, and what a v3 ESP keeps getting. A relay-plus-lag structure that
  limit-cycles at the cap in simulation (~6 Hz, ±4 A); do not develop it further. Distinct from
  the 1400 rpm over-speed *fault* line in `mc_config_common.c`, which is set deliberately high
  because a fault trip at speed cuts PWM into uncontrolled rectification.
- **Position servo** — `Ropetow_PositionControl()`, PD on multi-turn encoder counts.
- **ESP32 link** — `Src/esp_link.c` on USART2 (PA2/PA3, 115200), SLIP framing + CRC16, with a
  200 ms watchdog that commands 0 torque if the ESP goes silent after first contact.
  `protocol/trainsonic_link.h` is the **shared wire contract** — it is meant to be used verbatim by
  both firmwares, so bump `TSL_PROTOCOL_VERSION` on any incompatible change. v4 (2026-09-08) adds
  `brake_mA` to the heartbeat; v3 8-byte heartbeats are still accepted and keep the legacy
  control scheme (see speed-window control above). The ESP-IDF side is in
  `esp32/ts_link/` (not built by this project).

### Parameter flow
`pmsm_motor_parameters.h` + `drive_parameters.h` + `power_stage_parameters.h` (physical units) →
`parameters_conversion*.h` (fixed-point / timer counts, e.g. `CURRENT_CONV_FACTOR`,
`PWM_PERIOD_CYCLES`, `DEAD_TIME_COUNTS`) → consumed by init and the MC library. Changing a physical
parameter without regenerating leaves the converted constants stale — and regenerating reverts the
hand-edits. This tension is why the checklist docs exist.

## Working on the board

The operator interface is a **USB-CDC console with single-character commands**, parsed in
`Src/usbd_cdc_if.c` (numeric args like `t2000`, `s150`, `P1000`). It is the primary way everything
is tuned and tested; skim the `case` block there for the current set. Representative:

| Cmd | Effect |
|---|---|
| `t<mA>` / `s<rpm>` | torque / speed setpoint |
| `P`/`I`, `p`/`i` | current-loop / speed-loop gains, live |
| `g` | inject a step and stream a capture (feeds `step_tune.py`) |
| `y` / `Y` / `m` | start / abort / refine anti-cogging calibration |
| `X` / `n` | save / erase the cogging map in flash |
| `K` / `k`, `E<pct>` | anti-cogging FF on / off, amplitude |
| `x`, `w` | toggle MCSDK-native FW / legacy FW |
| `V<rpm>` | speed reference / cap (hard-clamped to 550) |
| `#`, `$<rpm>`, `%<mA>` | toggle **and pin** speed-window vs legacy governor (otherwise the heartbeat picks); fade band; default brake-side limit |
| `R` | acknowledge faults + restart at 0 A |

Host-side analysis scripts (run against saved console text, not the board):
`step_tune.py` (current-loop step response), `ripple.py` (Iq ripple FFT, labels mechanical vs
electrical orders), `cogging.py` (builds the anti-cogging table from a two-direction sweep).

Compile-time bring-up switches live in the `USER CODE PD` block of `main.c`: `ENC_ONLY` (never
start the motor, just stream the encoder), `STEP_MODE` (0 = current step, 1 = speed step,
2 = Iq ripple), `BOOT_OPENLOOP`. Several must be kept in sync with matching defines in
`mc_tasks_foc.c` (e.g. `STEP_DECIM`).

**Safety:** `StartAppTask` **auto-starts the motor on every power-up** with no operator interlock
(the code says so). On a machine that moves a load this is a hazard — assume the board may spin
the moment it is powered.

## Conventions

- Currents/speeds/voltages appear both as MCSDK-scaled `int16_t` and as `_F` float variants; match
  the convention of the function you are calling. Hand-written code converts with
  `CURRENT_CONV_FACTOR` / `CURRENT_CONV_FACTOR_INV`.
- Live-tunable state is a set of `volatile` `g_*` globals shared across ISR and thread context,
  declared in `mc_tasks_foc.c` and `extern`-ed at the point of use. Follow that pattern rather than
  adding headers.
- Historical prefix: most hand-written functions are still named `Ropetow_*` (the project's former
  name). Keep the prefix for consistency.
